## 1. מבוא ומטרה

Oficiency היא אפליקציית ווב (Web App) בעברית, בכיוון RTL, המיועדת לטכנאי שטח ולמנהלים בחברת Oficiency לניהול:
- דוחות שירות/תחזוקה לאתרי לקוחות
- תבניות דוחות חוזרות
- מסמכים ונהלי אתר
- מלאי ציוד וכלי עבודה, כולל מעקב מסירה/קבלה
- הרשאות משתמשים (טכנאים) באישור מנהל

האפליקציה מותאמת בעיקרון "Mobile-first" (טכנאי בשטח, בטלפון) עם תמיכה מלאה גם בדסקטופ.

**הערה לגבי PWA:** ה-HTML מסומן כ"ניתן להתקנה" (`apple-mobile-web-app-capable`, `theme-color` וכו') אך **אין בפועל קובץ `manifest.json` ואין Service Worker רשום**. כלומר זו אפליקציית ווב רספונסיבית עם מטא-תגיות PWA חלקיות, לא PWA מלאה עם עבודה אופליין אמיתית (יש רק גיבוי חלקי ל-localStorage + מטמון מקומי של Firestore).

## 2. משתמשים והרשאות (RBAC)

המערכת מבחינה בין שני סוגי משתמשים בפועל:

| תפקיד | הגדרה בקוד | יכולות עיקריות |
|---|---|---|
| **מנהל-על (Admin/Manager)** | אימייל קשיח: `sagi.tisson@oficiency.com` (קבוע `ADMIN_EMAIL_SINGLE` / `MANAGER_EMAIL` בכמה קבצים) | כל היכולות: יצירה/מחיקה/שינוי שם של תיקיות (אתרים), עריכת תבניות, אישור/דחיית בקשות הרשמה, ביטול גישה למשתמשים, הענקת/ביטול הרשאת עריכת תבניות לטכנאים, פאנל ניהול עם רשימת צוות ולוגים |
| **טכנאי (Technician)** | כל משתמש מאושר אחר | יצירה/עריכה של דוחות שהוא יצר, צפייה בלבד בדוחות של טכנאים אחרים, שימוש בתבניות (יצירת דוח מתבנית), ניהול ציוד, מסירת/קבלת ציוד. עריכת תבניות עצמן — רק אם הוענקה הרשאה מפורשת (ראו להלן) |

### הרשאת עריכת תבניות (`canEditTemplates`)
- הרשאה גרעינית נפרדת מ-`canEditReport` — שדה `canEditTemplates: boolean` במסמך `team_directory/{email}` של הטכנאי, כבוי כברירת מחדל.
- המנהל מעניק/מבטל אותה per-טכנאי מ-Manager Panel (תיבת סימון "עריכת תבניות" ליד כל חבר צוות ברשימת "צוות פעיל") — `apiSetTemplatePermission()`.
- נאכפת בשני מקומות: בצד הלקוח (`canEditTemplates()` ב-`api.js`, מסתיר/חוסם יצירה/עריכה/מחיקה/העברה/העתקה/ייבוא של תבניות ב-UI וב-`reports.js`) **וגם בפועל בשרת**, ב-`firestore.rules` — כתיבה למסמך המשותף `config/appstate` נדחית אם שדה `templates` השתנה והמשתמש אינו מנהל וללא ההרשאה, גם אם עוקפים את ה-UI. זהו יוצא דופן ביחס להערה בסעיף 3.1 (רוב בדיקות ה-RBAC הן client-side בלבד) — כאן יש אכיפה אמיתית בכללי האבטחה.
- מצב ההרשאה נטען עם כניסה לחשבון ומתעדכן בזמן אמת (`apiSubscribeTemplatePermission`, מאזין `onSnapshot`) — שינוי הרשאה על-ידי המנהל תוך כדי סשן פעיל של הטכנאי משפיע מיידית, בלי רענון דף.

### תהליך הרשמה ואישור
1. משתמש חדש נרשם עם שם/אימייל/סיסמה → נשמר כמסמך `pending` באוסף `registration_requests` (**כולל הסיסמה בטקסט גלוי ב-Firestore** — ראו סעיף סיכונים).
2. המנהל מאשר מה-Manager Panel → נוצר משתמש אמיתי ב-Firebase Auth (דרך אפליקציית Firebase משנית) והסטטוס משתנה ל-`approved`.
3. בכל טעינת אפליקציה/כניסה, המערכת בודקת שיש רשומת `approved` עבור אותו אימייל (`apiCheckUserApproval`), ומאזינה בזמן אמת (`apiSubscribeUserStatus`) כך שביטול גישה תוך כדי סשן פעיל מנתק את המשתמש מייד.
4. התחברות משתמשת ב-`browserSessionPersistence` — הסשן נמחק בסגירת הטאב; נכפית התנתקות בכל "סשן טרי" (טעינה ראשונה בטאב).

### הגבלת עריכת דוחות
- `canEditReport(r)`: מנהל יכול לערוך הכל. טכנאי רגיל יכול לערוך רק דוח שהוא יצר (`r.createdBy === email`). דוחות ישנים ללא `createdBy` נחשבים פתוחים לכולם (תאימות לאחור).
- דוח שאינו ניתן לעריכה נפתח במצב "צפייה בלבד" (באנר מותאם, כל השדות/כפתורים מנוטרלים, כולל לוחות חתימה).

### 3.1 תרשים כללי


## 4. מודל נתונים

### 4.1 State בזיכרון (`S` ב-`api.js`)
כל האפליקציה עובדת מול אובייקט state יחיד בזיכרון, המסונכרן חי מול Firestore:

```js
S = {
  reports: {},      // { reportId: reportObject }
  folders: {},       // { folderName: [reportId, ...] }
  templates: {},      // { templateId: {...} }
  attachments: {},     // { folderName: [attachment, ...] }  — מסמכים כלליים
  procedures: {},       // { folderName: [procedure, ...] }   — נהלי אתר
  equipment: {},          // { equipmentId: {...} }
  currentId, currentFolder, currentMode, currentTplId,
  currentUser, pad, customerPad, taskCounter, unsaved, ...
}
```

### 4.2 אוספי Firestore

| אוסף | תיאור | מפתח שמירה |
|---|---|---|
| `reports` | מסמך לכל דוח שירות (JSON מלא בשדה `report_data`) | `report.id` (frontend UID) |
| `config/appstate` | מסמך יחיד: `folders`, `templates`, `taskCounter` | קבוע |
| `attachments` | מסמכים כלליים לפי תיקייה/אתר | auto-ID |
| `procedures` | נהלים/הנחיות לפי תיקייה/אתר | auto-ID |
| `equipment` | פריטי ציוד/מלאי | auto-ID |
| `equipment_logs` | לוג היסטוריית מסירה/קבלה של ציוד | auto-ID |
| `registration_requests` | בקשות הרשמה (pending/approved/rejected) — **כולל סיסמה בטקסט גלוי** | auto-ID |
| `report_drafts` | טיוטות אוטומטיות (שדות טקסט + סטטוס משימות, ללא תמונות/חתימות) | `reportId` |
| `site_codes` | מיפוי תיקייה (אתר) → קוד קצר למספור דוחות (למשל "נשר מלט" → "NES"). כתיבה — מנהל בלבד. נכתב/נקרא מהאפליקציה; רק ה-Cloud Function קוראת ממנו בפועל להקצאת מספר | שם התיקייה |
| `counters` | מונה רציף פר-קוד-אתר (`{code}_SER`) — **נכתב ע"י ה-Cloud Function בלבד** (Admin SDK, עוקף rules), הלקוח לעולם לא כותב אליו ישירות | `{code}_SER` |

### 4.3 Firebase Storage — נתיבים

```
reports/{reportId}/img_*, sig_tech.png, sig_cust.png
attachments/{folderName}/{timestamp}_{filename}
procedures/{folderName}/{timestamp}_{filename}
```
תמונות וחתימות נשמרות תמיד כ-`data:` URL בזיכרון ומועלות ל-Storage בזמן השמירה (`apiSaveReport`) — כדי לא לחרוג ממגבלת 1MB למסמך Firestore.

## 5. יכולות פונקציונליות

### 5.1 ניהול דוחות שירות
- **אשף דוח חדש** (3 שלבים): בחירת סוג טיפול → שם ואתר → תבנית (אם רלוונטי).
- 6 סוגי דוח: ביקור תקופתי (עם תדירות), תקלה, טיפול נוסף, אחר, **יומן עבודה יומי**, **בדיקת ריתוך ויזואלי (Weld Inspection)** — לכל אחד מבנה טופס ייעודי.
- רשימת משימות דינמית: משימה רגילה (תקין/לא תקין + הערה), משימת טווח מספרי (min/max/יחידה + קריאה בפועל עם חישוב אוטומטי בטווח/חריג), וכותרות מדור (section) לחלוקה ויזואלית. ניתן לגרור ולסדר מחדש (SortableJS).
- **שכפול משימות** (בדוח ובעורך התבניות כאחד): כפתור שכפול בודד על כל שורה, וגם בחירה מרובה (תיבות סימון) + פס פעולה עם "שכפל נבחרים" לשכפול כמה משימות בבת אחת — מיועד לצ'קליסטים חוזרים (למשל אותה בדיקה על כמה מכונות). שכפול מעתיק את התיאור (ואצל משימת טווח — גם min/max/יחידה), אך מאפס סטטוס/קריאה/הערות — ההעתק הוא פריט חדש למילוי, לא העתקה של תשובה קיימת.
- **טופס "יומן עבודה יומי"**: יום/מזג אוויר/תיאור פרויקט, טבלאות פעילויות, עובדים יומיים, קבלני משנה, ציוד, הערות כלליות והערות מפקח.
- **טופס "בדיקת ריתוך ויזואלי"** (מבוסס דוח לדוגמה אמיתי — Daily Welding & Visual Inspection Report): שדות פרויקט/מסמך (Project, Installation/Piping Line, Contractor, Rev, No.Doc, WPS, Welding Process, Acceptance Criteria — לקוח/אתר/תאריך משותפים עם שדות הדוח הכלליים), וטבלת ריתוכים לפי-מפרק שבה כל שורה מייצגת חיבור בין שני רכיבים ולכן שדות החומר (Form/Spec/Heat No) כפולים — צד A וצד B — בדיוק כמו במסמך המקור: Drawing No., Joint No., סוג ריתוך (BW/FW), חומר (טופס/תקן/מס׳ התכה לכל צד), Nps/Sch, אלקטרודה (שורש/מילוי), Fit-Up (תאריך+תוצאה ACC/REJ), ריתוך (תאריך+חותמת רתך), בדיקה ויזואלית (תאריך+תוצאה ACC/REJ), סוג NDT. אישורים: Prepared By (חתימה דיגיטלית של הטכנאי), Inspected By ו-Witnessed By (שם+תאריך בלבד), Review By (חתימה דיגיטלית של הלקוח/סוקר).
- העלאת תמונות עם דחיסה/המרה אוטומטית (עד 1920px, JPEG, כולל fallback ל-HEIC/WebP), עריכה בלייטבוקס, מחיקה.
- חתימה דיגיטלית (טכנאי + לקוח) על גבי Canvas, נשמרת כתמונה.
- נספחים (appendices) לדוח — קבצים מצורפים.
- **שמירה אוטומטית של טיוטה**: כל הקלדה שומרת ל-`localStorage` מייד, ול-Firestore (`report_drafts`) עם debounce של 2.5 שניות — משוחזר אוטומטית בפתיחת הדוח אם עדכני יותר מהגרסה השמורה.
- שמירה, מחיקה (רכה — `isDeleted:true` תחילה לעדכון מיידי בכל הלקוחות המחוברים, ואז מחיקה קשה), איפוס סטטוסים, ייצוא JSON.

**מספור דוחות אוטומטי** (`מספר דוח` / `fNumber`) — אם לתיקייה (אתר) שהדוח שייך אליה יש `site_codes/{folderName}.code` מוגדר (למשל "נשר מלט" → `NES`), האפליקציה מציגה מספר בפורמט `OFIC-{code}-SER-{מספר תלת-ספרתי}`. שני שלבים נפרדים בכוונה, כדי שדוח שנוצר ונמחק/ננטש בלי להישמר אף פעם לא "ישרוף" מספר:
  - **תצוגה מקדימה (בפתיחת הדוח)** — `peekNextReportNumber` (read-only, לא כותב כלום) מציג את המספר הבא הצפוי כ-placeholder אפור בשדה ("...(משוער)") — זו רק הערכה חיה, לא מחייבת, ויכולה להשתנות אם דוח אחר נשמר קודם.
  - **הקצאה אמיתית (בשמירה הראשונה בפועל, לא ביצירה)** — רק כשלוחצים "שמור" (או Ctrl+S) בפעם הראשונה על דוח שעדיין אין לו מספר אמיתי, `assignReportNumber` מריצה טרנזקציית Firestore אטומית על `counters/{code}_SER` ומקבעת את המספר בפועל. השמירה האוטומטית-בשקט שקורית מיד ביצירת הדוח (לפני שהמשתמש נגע בכלום) **לא** מקצה מספר — היא רק שומרת את הדוח הריק עם `number` ריק.
  אם לתיקייה אין קוד אתר, השדה נשאר ריק/ידני לגמרי כמו שהיה — שום פעולה לא נחסמת. `assignReportNumber` גם רושמת שורה תואמת (best-effort — כישלון ב-Sheets לעולם לא מכשיל את הקצאת המספר עצמה) לגיליון Google Sheets משותף שהעסק כבר מנהל בו ידנית את המספור הזה, לפי כותרות העמודות בפועל שהיא מאתרת דינמית (לא לפי שורה/עמודה קבועה — לגיליון הזה יש כותרת ממוזגת ושורות ריקות מעל שורת הכותרות האמיתית, ועמודה A ריקה לגמרי, שתי מוקשים שגרמו לבאג אמיתי בפיתוח — ראו היסטוריה). שורות חדשות נכתבות בסוף הטבלה המלאה (לא בתוך הבלוק של האתר הספציפי) לפי בחירת המשתמש. מונה כל אתר ממשיך מהמספר האחרון שנרשם ידנית בגיליון ההיסטורי (זרעו ע"י `seedSiteCodes`, קריאה חד-פעמית מוגנת admin-only) — פערים/כפילויות שקיימים בהיסטוריה הידנית לא תוקנו במכוון, רק ההמשך מכאן ואילך אוטומטי. מספר שהוקצה בפועל **לעולם לא חוזר לשימוש** גם אם הדוח נמחק אחר כך (נוהג תקני בבקרת מסמכים — פער מתועד עדיף על כפילות). עריכת קוד אתר של תיקייה (תגית ליד שם התיקייה במסך האתר) מוגבלת למנהל בלבד.

**סיווג סטטוס דוח (ממתין / בתהליך / הושלם)** — מחושב על ידי פונקציה יחידה, `computeReportStatus()` ב-`api.js`, המשמשת בכל מקום שמציג את התג הזה (כרטיסי דוחות בדשבורד/בתיקייה, מונה "דו״חות בטיפול" בעמוד הבית, והשדה הנשמר ב-Firestore):
  - **ממתין** — אף סעיף ברשימת המשימות לא קיבל תוצאה עדיין (כולם עדיין `pending`).
  - **בתהליך** — לפחות סעיף אחד קיבל תוצאה, אך לא כולם.
  - **הושלם** — כל סעיף קיבל תוצאה כלשהי (תקין / לא תקין / בבדיקה / קריאת טווח), **או** שלדוח אין רשימת משימות בכלל (למשל קריאה לתקלה עם תיאור חופשי בלבד — אין לו התקדמות לעקוב אחריה, ואין כרגע כפתור "סמן כהושלם" נפרד).
  - חשוב: "הושלם" משמעו שכל הסעיפים **טופלו/נבדקו**, לא שכולם תקינים — דוח שבו כל הסעיפים סומנו "לא תקין" הוא הושלם באותה מידה כמו דוח שבו הכול תקין. זו הייתה נקודת הבלבול המרכזית לפני התיקון (ראו היסטוריה למטה).
  - עד 2026-08-25 היו שלוש מימושים נפרדים וסותרים של החישוב הזה (ב-`api.js`, `ui.js`, ו-`HomeTab.js`) שחלקו על שני דברים: האם דוח בלי משימות הוא "ממתין" או "הושלם", והאם תוצאה שלילית ("לא תקין"/"בבדיקה") נחשבת כטיפול בסעיף. אוחדו לפונקציה אחת.
- **ייצוא PDF** בצד הלקוח (RTL מלא, כותרת עם לוגו, תגי סטטוס, טבלת משימות, הערות, חתימות, עמוד נספחי תמונות נפרד). מפוצל לעמודי A4 סטנדרטיים (לא עמוד ענק אחד) — נקודת החיתוך בין עמודים מחושבת דינמית כדי ליפול על שורה לבנה בין משימות ולא באמצע שורה, וכותרת טבלת המשימות (# / תיאור / סטטוס / הערות) חוזרת בראש כל עמוד המשך; מספור עמודים ("X / Y") מוצג בפינת כל עמוד.
- **שיתוף**: פתיחת Gmail/Outlook web-compose עם טקסט מסוכם ("PDF יורד בנפרד לצירוף"), או Web Share API כשזמין.
- מצב צפייה-בלבד לדוחות שאינם בבעלות המשתמש הנוכחי.

### 5.2 תבניות (Templates)
- יצירה/עריכה בעמוד ייעודי (לא מודל), עם אותם סוגי משימות כמו בדוח.
- תבנית גלובלית (`folder: null`) או ספציפית לתיקייה/אתר.
- יצירת דוח חדש מתבנית (מעתיק את רשימת המשימות, הערות קבועות, נספחים) — פתוח לכל טכנאי.
- יצירה/עריכה/מחיקה/העברה/העתקה/ייבוא של תבניות, וכן שמירת דוח קיים כתבנית — **מוגבל למנהל או לטכנאי בעל הרשאת `canEditTemplates`** (ראו סעיף 2), נאכף גם ב-Firestore Rules.

### 5.3 תיקיות / אתרים (Folders)
- כל תיקייה מייצגת אתר לקוח. יצירה/שינוי שם/מחיקה — **מוגבל למנהל בלבד**.
- מחיקת תיקייה חסומה אם יש בה דוחות/תבניות/נהלים (חייבים לרוקן קודם).
- מסך אתר עם 5 טאבים: **היסטוריית דו״חות**, **תקלות**, **תבניות**, **נהלים**, **לוח טיפולים** (טבלה כרונולוגית: תאריך/טכנאי/סוג טיפול, לחיצה פותחת את הדוח).
- תגית "קוד אתר" ליד שם התיקייה (מוצגת רק אם מוגדר, או למנהל תמיד עם קריאה להגדיר) — קובעת את קוד מספור הדוחות האוטומטי של האתר, ראו 5.1.
- **טאב "תקלות"** — רשימת "תקלות פתוחות" באתר, נגזרת אוטומטית מהיסטוריית הדוחות עצמה, בלי מודל נתונים נפרד ובלי AI: משימות עם אותו תיאור טקסט (חוזרות בין ביקורים, בד״כ כי נוצרו מאותה תבנית) מקובצות יחד, וה**סטטוס האחרון בזמן** קובע אם הפריט עדיין פתוח. ברגע שדוח מאוחר יותר מציג את אותו תיאור משימה כ"תקין"/"בטווח", הפריט יורד מהרשימה אוטומטית — בלי פעולה ידנית. משימות "בבדיקה" (`under_review`) מוצגות בנפרד (ענבר) מ"לא תקין"/"חריג" (אדום). מכסה רק דוחות עם רשימת משימות רגילה (`r.tasks`) — לא `daily_log`/`weld_inspection`, ולא דוחות "תקלה" בטקסט חופשי בלי checklist. תג מספרי על הטאב מציג כמה תקלות פתוחות יש כרגע.

### 5.4 נהלים והנחיות (Procedures)
- העלאת קבצי PDF/Word/Excel לכל אתר, שמורים ב-Storage + Firestore.
- קבצי Office (`xlsx/xls/docx/doc`) נפתחים דרך Google Docs Viewer מוטמע; PDF/תמונות נפתחים ישירות.
- מחיקה מוחקת גם מ-Storage וגם מ-Firestore.

### 5.5 ייבוא/ייצוא
- **ייבוא JSON**: קובץ דוח/מערך דוחות שלם.
- **ייבוא Excel**: זיהוי אוטומטי של שורת כותרת, עמודה ראשונה = תיאור משימה, שנייה = הערה.
- **ייבוא Word**: חילוץ טקסט גולמי ופיצול לשורות/משימות.
- תצוגה מקדימה לפני אישור, עם בחירה אם לייבא כ"דוח" או כ"תבנית".
- ייבוא כתבנית ישירות מתוך מסך אתר ("ייבוא" בטאב תבניות).

### 5.6 ניהול ציוד (Equipment)
- מלאי ציוד מחולק לקטגוריות קבועות (כלי עבודה ידניים/חשמליים, ציוד לחץ וצנרת, מכשירי בדיקה, חומרים, ציוד בטיחות, ציוד כללי).
- כל פריט: שם, דגם, מספר סידורי, קטגוריה, סטטוס (במחסן/בשימוש/בתיקון), מחזיק נוכחי, הערות.
- חיפוש/סינון חי לפי שם או מספר סידורי.
- **מסך מסירת ציוד**: בחירת מוסר/מקבל (מרשימת משתמשים מאושרים + ערכי קבע "מחסן"/"שגיא"), בחירת פריטים מרובים, עדכון סטטוס אוטומטי, כתיבת רשומת לוג (`equipment_logs`), ופתיחת טיוטת מייל (`mailto:`) עם סיכום להעברה.
- סקריפט ייבוא חד-פעמי (`import-equipment.js`) לטעינת קובץ CSV קיים ("ציוד Oficiency – בקרה ומלאי") ישירות ל-Firestore.

### 5.7 דשבורד בית (Home)
- ברכה אישית לפי שעה, תאריך עברי מלא.
- גרף עמודות חודשי לפי סוג טיפול (תקופתי/תקלה/טיפול נוסף/אחר).
- KPI: דוחות בטיפול (pending/in_progress), סה"כ נהלים במערכת.
- כרטיס "המשך עבודה מהיר" — קופץ ישר לדוח האחרון שעודכן.
- **למנהל בלבד**: תצוגת תנועות ציוד אחרונות (10 אחרונות) בתוך דף הבית.

### 5.8 פאנל ניהול (Admin/Manager)
- רשימת בקשות הרשמה ממתינות עם אישור/דחייה (יצירה/מחיקה בפועל של חשבון Firebase Auth).
- רשימת "צוות פעיל" (כל המשתמשים המאושרים) עם אפשרות "ביטול גישה" (מוחק את חשבון ה-Auth ומעדכן סטטוס ל-`rejected`).
- מוצג הן במובייל (בתוך טאב הבית) והן בדסקטופ (פאנל נפרד).

### 5.9 ניווט וממשק
- **מובייל (≤768px)**: ניווט תחתון עם 3 טאבים (בית/דוחות/ציוד), כפתור FAB צף ליצירת דוח, סיידבר כמסך צד נגלל.
- **דסקטופ (>768px)**: שלושה טאבים עליונים, סיידבר קבוע עם עץ תיקיות/דוחות.
- תמיכה בסיבוב מסך (landscape) בטלפון עם זיהוי גובה מסך.
- תיקון ייעודי למקלדת iOS (מניעת "קפיצת" viewport).
- Splash screen בעליית האפליקציה, Toast notifications, מודלים (overlays) לכל פעולה הרסנית/משנית.
- תפריטי פעולה במובייל ("⋮") ממומשים כ-`<select>` טבעי של המערכת — בכוונה, כדי לעקוף בעיות z-index/touch ב-iOS Safari (ראה [[feedback_mobile_menus]] בזיכרון).

## 7. פריסה (Deployment)

- **Hosting**: `firebase deploy --only hosting`, `public: "frontend"`.
- **Functions**: `firebase deploy --only functions` (`functions/`, codebase `default`) — דורש תוכנית Blaze (pay-as-you-go) בפרויקט; לא זמין ב-Spark. נבדק תמיד קודם באמולטור (`firebase emulators:start`, פורט 5001) לפני deploy אמיתי.
- **גרסאות**: מספר גרסה מוטבע ב-query string של קבצי CSS/JS ב-`index.html` (`?v=1.5.22`) לצורך cache-busting על `index.html` עצמו ושני תגי ה-`<script>` הראשיים (`api.js`/`app.js`) — יש לעדכן ידנית בכל דיפלוי. **זה לא מספיק** לשאר קבצי ה-JS (ui.js, reports.js, כל `components/*`) הנטענים רק דרך `import` יחסי, ללא query string — לכן `firebase.json` מגדיר `Cache-Control: no-cache` על `/Js/**`, כך שכל קובץ JS תמיד עובר revalidation מול השרת (ETag, 304 זול) במקום להסתמך על caching היוריסטי של הדפדפן. בלי זה, גרסאות שונות של קבצים תלויים יכלו להסתנכרן לא נכון ולגרום ל-SyntaxError בזמן טעינה (התגלה ותוקן ב-2026-08-25).
- **סביבות**: זיהוי `localhost`/`127.0.0.1` מפעיל אוטומטית חיבור ל-Firebase Emulator Suite (Firestore :8080, Auth :9099, Storage :9199, UI :4000) המוגדר ב-`firebase.json`. אין קובץ `.env` — מפתחות Firebase כתובים ישירות בקוד (תקין עבור Firebase web config הציבורי מטבעו).
- קיים גם קונפיג Firebase חלופי מוער-בהערה (`reports-test-504cd`) לסביבת בדיקה — לא בשימוש כרגע.

## 8. סיכונים, חוב טכני וסוגיות פתוחות

> חלק זה קריטי לניהול הנדסי אחראי — הוא לא "יכולת" אלא רשימת פערים שזוהו בסריקה.

### 🔴 אבטחה — עדיפות גבוהה
1. **כללי Firestore ו-Storage פתוחים לחלוטין**: `allow read, write: if true` בשני הקבצים (`firestore.rules`, `storage.rules`). כל בקרת הרשאה (מנהל מול טכנאי, בעלות על דוח) נאכפת **רק בצד הלקוח**. כל אחד שיודע את ה-`apiKey` הציבורי (חשוף ממילא בקוד) יכול לקרוא/לכתוב/למחוק כל נתון ישירות מול ה-API של Firebase, כולל דוחות של לקוחות אחרים, ציוד, ואפילו לשנות סטטוס הרשמה משתמשים.
2. **סיסמאות משתמשים נשמרות בטקסט גלוי** באוסף `registration_requests` (כדי לאפשר יצירת/מחיקת חשבון Auth מאוחר יותר). כל מי שיכול לקרוא את ה-Firestore (=כל אחד, לאור סעיף 1) יכול לראות סיסמאות של כל הטכנאים וגם של המנהל בתהליך הרשמה.
3. **`playwright-test.js` המחובר לגיט מכיל אימייל וסיסמה בטקסט גלוי של חשבון המנהל בייצור** (`sagi.tisson@oficiency.com`). קובץ זה נמצא בהיסטוריית git (לא ב-`.gitignore`). מומלץ לשקול **החלפת הסיסמה** ולהוציא את הקובץ מהריפו (או לפחות מ-tracking עתידי) בהקדם.

### 🟠 חוב טכני
4. תיקיית `backend/` (FastAPI+SQLite) אינה בשימוש בייצור, מכילה נתיבים קשיחים ל-Windows, ומכפילה לוגיקה (יצירת PDF, CRUD דוחות) שכבר קיימת בצד הלקוח. מומלץ להחליט: להסיר, לתעד כארכיון, או להפוך לשירות backend אמיתי אם יש כוונה עתידית לאכוף הרשאות בצד שרת.
5. אין Cloud Functions לאכיפת לוגיקה קריטית (מחיקת דוחות, אישור משתמשים) — כל התהליך תלוי בקוד הלקוח שרץ בדפדפן.
6. אין בדיקות אוטומטיות (unit/integration) — קיים רק סקריפט E2E ידני יחיד (`playwright-test.js`) שדורש שרת מקומי פעיל ואינו רץ ב-CI.
7. אין `manifest.json`/Service Worker אמיתיים — הסימון כ"PWA" חלקי בלבד; אין תמיכה אמיתית בעבודה אופליין מלאה (רק גיבוי localStorage לטיוטות ומטמון Firestore).
8. `AdminPanel.js` ו-`ManagerPanel.js` מכילים לוגיקה חופפת (שתיהן מנהלות בקשות הרשמה) — ככל הנראה `AdminPanel` הוא שריד מגרסה קודמת שהוחלף ב-`ManagerPanel` המורחב יותר; כדאי לבחון איחוד.
9. מזהה המנהל היחיד קשיח בכמה מקומות בקוד (`api.js`, `app.js`, `HomeTab.js`, `EquipmentTab.js`, `AdminPanel.js`, `ManagerPanel.js`) — אין מודל תפקידים (roles) גמיש; הוספת מנהל נוסף דורשת שינוי קוד במספר קבצים.

### 🟡 הערות נוספות
10. גרסת ה-CSS/JS מנוהלת ידנית (query string) — תלויה בזיכרון המפתח לעדכן בכל דיפלוי (מתועד גם ב-[[feedback_working_style]] בזיכרון הפרויקט).
11. אין localization layer — כל הטקסטים בעברית קשיחים (hard-coded) בתוך הקוד, ללא i18n.

## 9. סיכום

Oficiency היא אפליקציית Firebase חד-Repository, מבוססת ES Modules ללא build step (אין Webpack/Vite/bundler — כל קובץ JS נטען ישירות כמודול), עם State גלובלי בזיכרון (`S`) המסונכרן חי מול Firestore. המערכת בשלה מבחינה פונקציונלית (ניהול דוחות, תבניות, אתרים, ציוד, הרשאות בסיסיות), אך **אינה עומדת בסטנדרט אבטחה production-grade** בשל כללי Firestore/Storage הפתוחים לחלוטין ואכיפת ההרשאות בצד לקוח בלבד — זו הנקודה הדחופה ביותר לטיפול לפני שהמערכת "ניהולית ובטוחה" באמת.
